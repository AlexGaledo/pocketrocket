# P2: Take over, hand back, approvals while away

User-visible changes for the `[Unreleased]` section of `CHANGELOG.md` (the integrator merges them in).

## Added
- **Take over, hand back, pause.** Each bot's computer is driven by the bot (default), by you, or by
  nobody (paused). The Screen tab and a bot's DM header have **Take over**, **Hand back** (with an optional
  note for the bot) and **Pause / Resume**. While the bot has control the viewer only watches: x11vnc runs
  view-only and the noVNC page opens with `view_only=1`. Take over and you can click and type; the viewer
  reloads interactive.
- **The control interlock holds in bypass mode too.** While you have control (or the bot is paused) its
  desktop and Browser tools refuse with "the user has control; wait", at every layer: the desktop tool
  handlers, the HTTP MCP endpoint used by non-Claude providers, a Claude PreToolUse hook on
  `mcp__browser__*` / desktop tools, and the permission broker. Without per-bot computers, a person in
  control of the one shared screen stops every bot's computer tools.
- **Pause bot.** A paused bot starts no turns; messages to it wait in its lane and run when you resume it.
- **Bots can ask for you.** New hub tool `request_takeover({ reason })` (bots with Browser or Desktop):
  it posts a takeover card ("@shopper needs you: log in to example.com"), gives you control and waits. Hand
  back and the bot gets your note and continues. If nobody hands back within 10 minutes the bot's turn ends
  ("parks") and your hand-back starts a new turn with the note. A takeover nobody answers is given up after
  24 hours and control goes back to the bot. A note you leave on a hand-back without a request rides along
  with the bot's next turn.
- **Routines no longer fail at 3 a.m. on an approval.** A turn started by a routine (or, from P5, a trigger)
  whose card nobody answers within 10 minutes parks instead of being denied: the card stays open (also
  across a hub restart), the turn ends and frees its slot, and the routine run stays open. When you answer,
  hours later, the bot is resumed on the same thread with "Approval granted/denied"; an allowed call goes
  through once without a second card, and the run then closes. A card parked for 24 hours
  (`POCKETROCKET_MAX_PARK_HOURS`) is denied. Turns you started still time out after 10 minutes as before.
- **Approval rules.** After **Allow for this session** a card offers **Make this a rule?** with the pattern
  it would cover (the exact command or path; end with `*` for a prefix, or `*` for any call). **Settings ›
  Bots › Approval rules** lists the rules and revokes them. Rules apply to routine turns too. Only you can
  create one (REST, hub token); no bot tool or MCP route reaches them. An allow rule never covers a command
  flagged as dangerous, and **integration writes (send mail, post to Slack, ...) still ask on every call**.

## Changed
- "Allow for this session" is now a session row in `approval_policies` (bot + tool + exact subject) instead of
  an in-memory set per bot and tool, so it covers the same command again rather than every use of the tool.
  Session rows are dropped at every hub start; a dangerous command is allowed once and not remembered.
- Without per-bot computers the shared screen follows the same rule: view-only until someone takes over.
- `deploy/computer.sh` starts each computer's x11vnc with `-viewonly` (`VNC_VIEWONLY=1` in `deploy/screen.sh`).
- REST: `GET /api/control`, `GET|PUT /api/computers/:botId/control` (`{ control: agent|user|paused,
  holder?, note? }`), `GET|POST /api/approval-policies` (`{ approvalId, pattern? }` or `{ botId, tool,
  pattern }`, `decision` allow|deny), `DELETE /api/approval-policies/:id`, `GET /api/approvals/parked`. The
  `/api/screen` URL and the ticket redirect carry `&view_only=1` while the bot has control.
- WS: `computer.control` (`ControlStatus`) and `policies.changed`. New message kind `takeover`
  (`TakeoverPayload`); `ApprovalPayload.parked`.

## Known limits
- Control state lives in memory: after a hub restart every computer is back to `agent` and an open takeover
  card shows as expired (its turn is gone anyway). Parked approvals do survive a restart.
- noVNC's `view_only` flag is only the UI-side guard; the real one is x11vnc's view-only mode, toggled with
  `x11vnc -R viewonly|noviewonly` over the display's X property. Not verified on a VPS (see below).
- The hand-back `holder` is a per-browser id the client picks; it is informational, not an authorization.

## Not verified (VPS only)
- `x11vnc -display :20n -auth <cookie> -sync -R viewonly|noviewonly` against a running per-bot computer, and
  that a viewer really cannot click while view-only. Tests use a fake `VncControl`.
- The Claude CLI honouring a PreToolUse `deny` for `mcp__browser__*` in `bypassPermissions` mode end to end
  (unit tests check the hook is installed and answers deny; the SDK itself is mocked).
- A real login flow through `request_takeover` (manual test in the spec).

## For P6 (teach by demonstration)
- Force user control while recording: `hub.control.set(botId, 'user', { holder: 'recorder' })` (or `PUT
  /api/computers/:botId/control { control: 'user' }`); the bot's computer tools then refuse and the viewer
  is interactive. End with `hub.control.set(botId, 'agent')` (add `note` to tell the bot what was shown).
  `hub.control.get(botId)` / the `computer.control` event report the state.
- The bot's display and CDP while recording: `await hub.computers.acquire(botId)` (keeps it from an idle stop
  and starts it if asleep; call `release()` when done) or `hub.computers.existingEndpoint(botId)` for a
  computer that has a slot. The `ComputerEndpoint` has `display` (`:20n`), `xauthority`, `cdpUrl`
  (`http://127.0.0.1:940n`, for a second CDP client), `home`, `filesDir` and `vncPort`.
