# P6: Teach by demonstration and skill refinement

User-visible changes for the `[Unreleased]` section of `CHANGELOG.md` (the integrator merges them in).

## Added
- **Teach a bot by showing it.** On a server hub with per-bot computers, the Screen tab has **Teach**. Press it
  (optionally say what you will show), do the task on the bot's computer, then press **Done**. While recording you
  have control of the computer (the bot's Browser and Desktop tools wait, as with Take over), and a static red dot
  shows "Recording · N steps · M screenshots". Done hands control back with a note to the bot; **Hand back** from
  the control bar also ends the recording. The desktop app (local mode) and servers without per-bot computers do
  not show Teach.
- **What is recorded.** Into `data/computers/<botId>/recordings/<timestamp>/`: `trace.jsonl` with page
  navigations, clicks (a robust CSS selector, the element's role and accessible name, its text), typed values
  (saved when you leave the field or press Enter), special keys (Enter, Tab, Escape, arrows, Ctrl/Alt
  shortcuts), form submits and downloads; the active window's title every two seconds (for apps that are not the
  browser); a screenshot (`frames/*.png`) after each click; and `meta.json`. Recordings stay on the server and are
  erased with the bot.
- **Secrets are redacted while recording, not afterwards.** Typing into a password field, any field whose
  `autocomplete` mentions `password` or starts with `cc-`, a `one-time-code` field (or one named like a
  password, card number, CVC or code) is saved as `«secret»`, never the value. The page script decides this and
  the hub checks every event again. No screenshot is kept while such a field has focus, while a card number or
  code you typed is still on the page, or when the click itself was on one. Credential-looking URL query values
  (`token`, `code`, `session`, ...) are replaced too.
- **Limits per recording:** 2000 steps, 200 screenshots, 64 MB, 30 minutes. The indicator says which limit was
  reached; the recording keeps what it has.
- **Distill.** Each finished recording has **Distill**: one Sonnet call (no tools, at most $0.25) writes a
  `SKILL.md` with parameters, steps (selectors as hints next to roles and names), checks and notes. A new name
  becomes a bot-authored skill **pending review**, exactly like `save_skill`; a name already in the pool becomes
  a pending **version** of that skill.
- **Skill versions.** A skill now has a live version and a history. Proposed versions come from a demo, from your
  correction, from a bot's reflection, or from a bot calling `save_skill` with a name already in the pool (which
  used to overwrite the skill). The Skills tab marks skills with versions to review, and the skill view lists
  every version with a line diff and **Approve** / **Reject**. Approving replaces the live `SKILL.md` and reaches
  every bot using the skill on its next turn; nothing is ever applied without it. At most 10 versions wait per
  skill.
- **Correct a skill.** Under a skill, "Correct this skill" takes a sentence ("no, use the Export button"); a
  Sonnet call (at most $0.25) proposes the revised `SKILL.md` as a new pending version with that note.
- **Reflection (opt-in per bot, off by default).** Skills tab › "Suggest skill fixes after runs": after every N
  runs (3, 5, 10 or 20; default 5) of one of the bot's approved skills, a one-shot pass reads that run and may
  propose a fix as a pending version, with a line in the room saying so. It runs on Haiku through the model router
  (cause `reflection`), costs at most $0.05 a pass and $0.25 a day per bot, and shows under Usage as reflection.
- REST: `GET /api/computers/:botId/recorder`, `POST .../recorder/start { title? }`, `POST .../recorder/stop`,
  `GET .../recordings`, `GET|DELETE .../recordings/:id`, `POST .../recordings/:id/distill { name?, hint? }`,
  `GET /api/skills/:id/versions`, `GET|POST /api/skills/:id/versions/:vid` (`{ decision: approve|reject }`),
  `POST /api/skills/:id/corrections { text }`, `GET|PUT /api/bots/:id/skill-reflection`. WS: `recorder.state`
  and `skills.changed`. `Skill` gains `version`, `parentId` and `pendingVersions`.
- **Phones** may watch a recording, end it (Done) and read recordings, versions with their diff and the reflection
  setting. Starting a recording, distilling, corrections, the reflection opt-in and approving or rejecting a
  version stay desktop actions, like the rest of skill review.

## Not user-visible
- Migrations 60–63, registered as the P6 block `[60, 69]`: `skills.version`, `skills.parent_id`, version metadata
  (`origin`, `note`, `created_at`, `decided_at`) and the `skill_reflection` / `skill_reflection_runs` tables. A
  candidate version is a `skills` row with `parent_id` set and the name `<skill>@v<n>` (never a valid pool name);
  `Repos.listSkills` leaves those rows out and `materialize` never copies one. Its files are
  `data/skills/.versions/<skill>/v<n>/{SKILL.md,BASE.md}`.
- New: `services/Recorder.ts`, `recorderPage.ts` (the page script and the shared secret-field rules),
  `cdpClient.ts` (CDP JSON over the existing `ws` dependency), `SkillDistiller.ts` (`runOneShot`, the
  AutoMemory-style options with the caller's model and budget), `SkillReflection.ts`, `lineDiff.ts`,
  `db/skillVersions.ts`, `api/teach.ts`; `@pocketrocket/shared` `teach.ts`.
- The recorder is a second CDP client: it attaches to page and iframe targets (flat sessions) and runs its script
  and binding in an isolated world, so the page can neither see nor call it. It does not change download
  behaviour or anything else Playwright MCP relies on.
- `RoomRouter.skillReflection`, `Repos.messagesOfTurn`, `SkillService.proposeVersion / decideVersion /

- Test fixture `packages/hub/test-fixtures/teach/checkout.html`; `Recorder.chrome.test.ts` runs the recorder
  against a real headless Chrome/Chromium when one is installed (skipped otherwise; `CHROME_PATH` forces one).

## Known limits
- The recorder state lives in memory: a hub restart ends an open recording and control is back to the bot, as for
  P2. After a crash the recording is listed as interrupted and can still be distilled.
- Typed text is captured from input and textarea fields and contenteditable elements in the browser only.
  Typing into a desktop app is not recorded (only its window title), and no screenshot is taken there.
- Screenshot redaction knows about secret fields in the browser. A secret shown by a desktop app, or as plain text
  on a web page that is not in a form field, can appear in a kept frame.
- A cross-origin iframe the recorder cannot attach to (a browser policy) is not traced; clicks there are not
  recorded and take no screenshot.
- Distill and corrections need the Claude provider and its CLI on the hub, like auto-memory.

## Not verified (VPS only)
- `scrot` and `xdotool` on a per-bot display with its `.Xauthority` (tests use fakes for both).
- The recorder against a bot's own Chromium on `127.0.0.1:940n` while Playwright MCP is attached to it. The CDP
  side was run against a real headless Chrome on Windows (`Recorder.chrome.test.ts`), not on a VPS computer.
- Distill quality: whether a distilled skill replays the demonstrated task ("manual on 3 sample tasks" in the
  spec). Tests use a fake model.
